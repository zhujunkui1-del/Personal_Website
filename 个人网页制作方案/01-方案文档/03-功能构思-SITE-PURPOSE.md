# 网站功能构思

> 本次重写。已废弃基于错误前提的旧版本（见文末"作废说明"）。
> 参考对象仅用于**风格**：`素材\` 的图与 `网站资源.txt` 的站点都与本网站的用途无关。

---

## 0. 你明确要的五件事

| # | 功能 | 本质 |
|---|---|---|
| 1 | 作品集 | 展示能力 |
| 2 | 内容输出 | 持续更新、吸引回头 |
| 3 | 名片 | 我是谁 + 怎么找我 |
| 4 | 留言墙 | 访客互动 |
| 5 | 隐藏式音乐播放器 | 氛围 / 彩蛋 |

这五个不是并列的。它们分属**三个层次**，而且互相依赖：

```
┌─── 展示层（存在即价值）─────────────┐
│  作品集  ·  名片                    │
├─── 内容层（需要持续投入）───────────┤
│  内容输出（文章 / 教程 / 资源）      │
├─── 交互层（制造留痕与情绪）─────────┤
│  留言墙  ·  隐藏音乐播放器           │
└─────────────────────────────────────┘
```

**层次含义**：
- 展示层没做好，站就不成立
- 内容层决定访客**会不会回来**
- 交互层决定访客**会不会记住你**

## 1. 核心矛盾：三重身份怎么不分家

你说它同时是作品集 / 内容平台 / 名片。这三者的**首页诉求是冲突的**：

| 身份 | 首页该突出什么 |
|---|---|
| 作品集 | 作品图，越大越好 |
| 内容平台 | 最新文章，越新越好 |
| 名片 | 我是谁 + 联系方式，越清楚越好 |

**解法：不放在同一屏，用顺序和层级分开。**

已经敲定的 `final_home_bg.png` 结构其实天然解决了这个问题：

```
首屏    巨字姓名 + 主视觉 + 信息卡四行   ← 名片（我是谁）
作品区  06 SELECTED WORKS + 四张卡       ← 作品集（我能做什么）
```

**只需往下补两块**：

```
笔记区  最新 3 篇                        ← 内容（我在持续输出）
联系区  社群链接 + 留言入口              ← 名片收尾 + 交互层入口
```

于是首页变成一条完整的说服链：
**我是谁 → 我能做什么 → 我一直在做 → 怎么找我 / 怎么留下痕迹**

> 这就是 `CONCEPT.md` 里"外壳是工程图纸"的延伸 —— 首页是**一条动线**，不是四块内容拼盘。

## 2. 逐项功能设计

### 2.1 作品集

| 项 | 设计 |
|---|---|
| 首页 | 只放 **4 件精选**（`final_home_bg` 已定） |
| 列表页 | `/work` 全部作品网格，按年份 / 类型筛选 |
| 详情页 | `/work/[slug]` 图组 + 元数据（年份 / 类型 / 工具 / 角色） |
| 交互 | hover 灰度→原色；点击进详情；`←/→` 键盘切换 |
| 不做 | 无限滚动、多级分类嵌套 |

**关键决策**：作品数量。若少于 8 件，`/work` 列表页可以省掉，首页直接展开全部。

### 2.2 名片

| 项 | 设计 |
|---|---|
| 内容 | 一句话定位 + 技能标签 + 邮箱 + 社群链接 + 所在地 |
| 位置 | 首页信息卡 + 独立 `/about` |
| 强化 | `final_home_bg` 里的坐标 `37.2304 N / 121.4737 E`、`● ONLINE` 状态 —— 用伪技术细节建立"可联系感" |
| 导出 | 可选：一键保存为 vCard（`.vcf`），手机上直接存联系人 |

> vCard 是个被低估的小功能：访客点一下就把你存进手机通讯录，比"复制邮箱"有效得多。

### 2.3 内容输出

| 项 | 设计 |
|---|---|
| 形态 | 文章 / 教程 / 资源分享 / 随笔 |
| 列表 | `/notes` 带分类筛选与时间轴 |
| 详情 | `/notes/[slug]`，代码块用 HUD 风格（等宽 + 左侧 1px 线 + 零圆角） |
| 更新提示 | 首页显示"最新更新"日期 —— 让访客知道你**还活着** |
| 订阅 | 可选 RSS（几乎零成本，老派但有效） |

**关键决策**：内容从哪来。
- 你**在这个站写** → 需要后台或 Markdown 文件
- 你**在别处写**（公众号 / 语雀 / B站专栏） → 这个站只做导流与摘要

> 这决定了技术栈复杂度，是最需要你定的一项。

### 2.4 留言墙 ★ 需要后端

这是**唯一一个必须引入服务端**的功能。纯静态站无法存留言。

| 方案 | 成本 | 优点 | 缺点 |
|---|---|---|---|
| **A. 第三方评论服务**<br>（Giscus / Waline / Twikoo / Artalk） | 免费 | 半小时接完，自带反垃圾、通知 | 数据在别人服务器；样式需魔改才能贴合你的设计 |
| **B. Serverless + 数据库**<br>（Cloudflare Workers + D1 / Vercel + KV） | 免费额度够用 | 完全可控，样式随意 | 要写一点后端代码 |
| **C. 自建轻量后端**<br>（一台小服务器 + SQLite） | 需服务器 | 完全自主 | 要运维，可能被刷 |
| **D. 无后端方案**<br>（留言存 GitHub Issues / 表单转邮件） | 免费 | 零后端 | 体验差，不算真"留言墙" |

**我的建议：方案 A（Artalk 或 Twikoo）起步**，理由是留言墙的价值在"有人留言"，不在技术自主。反垃圾是刚需，第三方服务已经解决了这个最麻烦的问题。等真有人来了、样式必须彻底定制时，再迁到方案 B。

**留言墙的设计要贴你的视觉**：不要做成普通评论区。建议做成**卡片墙**——每条留言一张直角卡片，等宽字署名 + 日期，零圆角，与作品卡同构。

### 2.5 隐藏式音乐播放器 ★ 两个真问题

**"隐藏"是聪明的** —— 因为你绕开了浏览器的自动播放限制（浏览器禁止无交互自动播放音频，必须用户先点击）。隐藏入口 = 用户主动触发 = 合法且不烦人。

**真问题 1：版权**
不能放商业音乐。可行路径：
- 自己创作 / 委托创作
- CC0 / 公共领域音乐（Free Music Archive、Pixabay Music）
- 已授权免费使用的独立音乐人作品
- 只放 30 秒片段（仍有风险，需谨慎）

> 这是**法律风险**，和 `CONCEPT.md` 里提醒的字体授权是同一类问题。放上去之前必须确认授权。

**真问题 2：形式**
"隐藏"的几种做法：

| 形式 | 保密程度 | 说明 |
|---|---|---|
| 角落一个小圆点 / 声波符号 | 低 | 细心的人能看到，最实用 |
| 招牌上的某个字可点 | 中 | 与设计语言融合，彩蛋感强 |
| 输入密码 / Konami 码 | 高 | 极难发现，但可能永远没人用 |
| 滚动到某位置触发 | 中 | 与动效结合 |

**建议**：用**中等保密**——把入口做进设计的某个符号里（比如 `final_home_bg` 顶栏那个 `＋`，或 `● ONLINE` 状态点）。既保持"隐藏"的趣味，又不至于真的没人发现。

**形式建议**：底部一条极细的横条，随音乐节拍起伏（声波可视化）。这样它既是播放器又是**动效装饰**，符合你的 HUD 美学。

## 3. 功能优先级

### P0 —— 没它站不成立
```
作品展示（首页精选 + 详情页）
名片信息（首页信息卡 + /about）
响应式
图片优化与懒加载
基础 SEO
```

### P1 —— 让站真正活起来
```
/work 列表页 + 筛选
/notes 内容区
隐藏音乐播放器
留言墙
入场动效
```

### P2 —— 打磨
```
搜索
RSS
vCard 导出
声波可视化
留言墙卡片墙样式深度定制
```

## 4. 三个必须你定的问题

| # | 问题 | 为什么关键 |
|---|---|---|
| 1 | **作品有多少件？** | 少于 8 件 → 可省掉 `/work` 列表页，首页直接铺开 |
| 2 | **内容在哪写？** | 决定技术栈。站内写 → 要 Markdown 或后台；别处写 → 只做导流 |
| 3 | **音乐哪来的？** | 版权问题。没有合法音源，这个功能就不能上 |
| 4 | **留言墙接受第三方服务吗？** | 接受 → 半天搞定；不接受 → 要写后端，工期明显变长 |
